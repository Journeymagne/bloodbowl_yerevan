**Дата разбора:** 2026-08-22
**Утечка закрыта:** 2026-08-21, коммит `5ff1952`
**План работ:** [`docs/superpowers/plans/2026-08-22-security-hotfix-closeout.md`](superpowers/plans/2026-08-22-security-hotfix-closeout.md)

Собранные материалы лежат на сервере в `/root/bb-incident-2026-08-22/`
(`caddy.log`, `postgres.log`, `env.bak`, `gata_league.sql`, права `600`).

## Главный вывод

Признаков использования утёкших учётных данных не найдено. **Это не то же самое,
что их отсутствие:** ни один из двух журналов, способных такое зафиксировать, не был
включён. Пароли меняются исходя из того, что они скомпрометированы.

Отдельно и независимо от утечки обнаружен непрерывный перебор паролей к Postgres
с 2026-07-12 по 2026-08-22, использующий открытый наружу порт `5433`.

## Чем мы не располагали

| Журнал | Состояние | Следствие |
|---|---|---|
| Access-лог Caddy | **выключен** (`handled request` — 0 записей, директивы `log` в Caddyfile нет) | Успешное скачивание `/.env` не оставило бы следа. Проверка «обращений с кодом 200 не найдено» пуста по построению. |
| `log_connections` в Postgres | **выключен** (умолчание образа `postgres:16`) | Успешное подключение к базе не логируется. В журнале видна только та часть попыток, у которой не было пароля. |

Обе асимметрии работают в одну сторону: неудачи видны, успехи — нет.

## Что в журналах было

### Caddy — 1011 строк, только уровень `error`

Обращения к `/.env`, `/.env.local`, `/.env.production`, `/.env.example`, `/.git/HEAD`,
`/api/.env`, `/docker-compose.yml`. Все — `status 502`,
`dial tcp 172.18.0.1:3002: i/o timeout`, домен `bb.shitpostsoftware.com`, интервал
**2026-07-12 12:37–12:40 UTC**: день первичной установки, приложение на `3002` тогда
ещё не отвечало. User-Agent'ы `Go-http-client/1.1` и `Silvy X Ran` — типовые сканеры.

К окну, когда файлы действительно отдавались, эти записи отношения не имеют.

### Postgres — 108 650 строк, вся жизнь контейнера с 2026-07-12

**35 676 неудачных аутентификаций.** Первая — `2026-07-12 16:41:32 UTC`, последняя —
`2026-08-22 11:18:01 UTC`, то есть перебор шёл во время самого разбора. Темп ровный,
около одной попытки в минуту, сорок один день подряд.

Плюс 37 записей `unsupported frontend protocol` — сканеры определяли, что за сервис

**Ключевая проверка: `gata_admin` — 0 попыток.**

Это имя не угадывается по словарю. Узнать его можно было только из `.env`,
`docker-compose.yml` или `server/init.sql` — а все три какое-то время отдавались
наружу. Ноль попыток означает, что перебор вёлся ботами, самостоятельно нашедшими
открытый порт сканированием, и с утечкой в раздаче статики не связан.

Обратная сторона: тот, кто прочитал `.env`, знал бы и имя, и пароль, вошёл бы с
первой попытки и не оставил бы в журнале ничего.

### SSH — без замечаний

`root`: один ключ `bloodbowl-league-deploy` — ключ GitHub Actions из деплой-воркфлоу.

### База — без замечаний

Роли: одна, `gata_admin`. Таблиц семь, все созданы `server/init.sql`: `users`,
`sessions`, `seasons`, `season_rounds`, `season_pairings`, `season_entries`,
`saved_teams`. Ничего постороннего.

Администраторы приложения — два, оба подтверждены владельцем:

`updated_at` у `admin` совпадает с деплоем фикса: `ensureAdmin()` перезаписывает хеш
пароля значением из `.env` при каждом старте процесса.


После переноса файла с секретами повторно, полным набором:

```
/.env /.env.example /.git/config /package.json /server/init.sql
/docker-compose.yml /server/config/env-file.mjs                        ->  404 ×7
/ /index.html /src/app.js /public/data.en.json /public/data.ru.json
/api/health                                                            ->  200 ×6
nc 51.81.86.51:5433                                                    ->  Operation timed out
заголовки ответа                                                       ->  4 из 4, Server скрыт
```

Файл с паролями лежит в `/etc/bloodbowl-league/.env` (`600`, `root:root`).
На сервере `resolveEnvFilePath` печатает именно этот путь, и приложение отвечает
`200` **после** удаления `/opt/bloodbowl-league/.env` — то есть читается новое
расположение, а не остаток по старому. Защита стала двухслойной: белый список
путей, и за ним пусто.

Перебор паролей к Postgres прекратился вместе с закрытием порта: последняя
зафиксированная попытка — `2026-08-22 11:18:01 UTC`, за несколько минут до применения
привязки к `127.0.0.1`.

## Что из этого следует

1. **Порт `5433` закрывается в первую очередь** — он под активной атакой независимо
   от утечки. Это сделано в фазе 2 плана.
2. **Пароли считаются скомпрометированными** и меняются, несмотря на отсутствие
   следов: инструментов увидеть след у нас не было.
3. **Включить журналирование стоит отдельной задачей.** Если бы access-лог Caddy и
   `log_connections` были включены, этот разбор дал бы ответ, а не оговорку. В объём
   текущих работ не входит.
