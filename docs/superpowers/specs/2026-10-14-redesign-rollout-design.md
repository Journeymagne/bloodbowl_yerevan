# Редизайн 3.0: исполнение цепочкой PR и переезд на прод

**Тип документа:** design spec (как исполнять и выкатывать). **Что** строим — в `2026-10-14-redesign-design.md` (дальше «спека 3.0»), **по каким этапам** — в `plans/2026-10-14-redesign.md` (дальше «план 3.0»). Этот документ отвечает на два вопроса: как Claude с агентами проводит этапы цепочкой PR и как перевезти боевой сайт на 3.0 быстро, безопасно и без потери данных.
**Основа:** ветка `rd/00-plan` поверх `redesign`, коммит `bd6a70a`; прод — 2.0.0 на VPS (pm2, Postgres 16 в Docker, общий Caddy-контейнер `paint-day-caddy`).

---

## 0. Решения владельца (2026-10-14)

1. **Выкат — подход A:** сначала маленький релиз **2.1.0** в `main` со всей механикой переезда, он проверяется на проде. Потом один переезд: PR `redesign → main` (§1, §6).
2. **Самостоятельность.** Этапные PR в `redesign` Claude открывает и вливает сам, после всех проверок и ревью агентами. Владелец смотрит вехи M1–M5 (§2.4). В `main` вливает только владелец, на прод ходит только он: у Claude нет SSH.
3. **Параллельность.** Два трека на старте, дальше не больше двух экранных этапов одновременно, слияния в `redesign` по одному (§2).
4. **Окно переезда** — любой тихий момент, тур может быть открыт. Условие: нет начатых матчей с незавершёнными итогами и нет неподтверждённых счетов. Простой — до часа, со страницей техобслуживания (§6).
5. **Бэкапы.** К ночным дампам добавляются автоматический дамп перед миграцией и копия дампа дня X на Mac владельца. Снапшот VPS и холодная копия тома не делаются (§4).
6. **Репетиция** — локально, на обезличенной копии боевой базы, на каждой вехе (§3).
7. **PR #9** (UI polish p8) закрывается. Полезное из него (`render-table.mjs`, правки сборки, глоссарий) переносится в `redesign` этапом 01.
8. **§9.6 спеки 3.0 закрыт.** У тренера один путь: подготовка → итоги. `proposeGameResult` остаётся на сервере для админа. Форма быстрого счёта у тренера удаляется.
9. **Стадия команды при переезде.** `active` получает команда с неотозванной заявкой в текущий сезон **или** хотя бы одним сыгранным матчем (лиговым или товарищеским, с подтверждённым счётом или итогами). Остальные — `draft`, в `active` их переводит админ. Это **заменяет §0.6 спеки 3.0**.
10. **Ничего не удаляется.** Текущий сезон продолжается: миграции только добавляют. Погибшие из матчей, завершённых через итоги на сайте, переносятся в новую таблицу. Остальных админ дописывает вручную (§5.1).
11. **Источники правды.**
    - Правила лиги — `content/Gata/` (RU-зеркало `content/Gata-ru/`) и их реализация в `src/domain/`. Если контент и код расходятся **между собой**, Claude останавливает трек и спрашивает владельца, ни одну сторону молча не выбирает. Расхождения макета с кодом правятся по коду (§0.1 спеки 3.0) без вопроса.
    - Живой сайт 2.0 (bloodbowlyerevan.shitpostsoftware.com) — эталон «как работает сейчас», только чтение, без входа.
    - Первоисточники xlsx/docx не нужны.

## 1. Релиз 2.1.0 «подготовка к переезду» (ветка от `main`, PR в `main`)

Всё, что нужно в день X, заранее работает на проде. После 2.1.0 `main` заморожен: в него идут только фиксы багов, каждый сразу вливается в `redesign`.

### 1.1 Режим техобслуживания в сервере

Переезжает сюда из этапа 3 плана 3.0 и заменяет §4 «Техобслуживание» спеки 3.0.

- **Флаг-файл** `/etc/bloodbowl-league/maintenance.json`, путь переопределяется через `MAINTENANCE_FILE` в env-файле. Поля `{kind: "planned"|"unplanned", startsAt, endsAt}`. Сервер перечитывает файл на лету (`stat` не чаще раза в 2 секунды), перезапуск не нужен. Если файл есть, но битый, считается, что режим включён, `kind: "unplanned"` без времени, и в лог уходит предупреждение.
- **Пока флаг есть:**
  - любой не-API путь отдаёт `503`, `Retry-After` и страницу из §1.2. Исключение — статика самой страницы (`/public/maintenance/*`, `/assets/fonts/*`);
  - `/api/*` отвечает `503` с кодом `MAINTENANCE` (в `API_ERRORS` и обоих словарях);
  - `/api/health` отвечает `200` и `maintenance: {kind, startsAt, endsAt}`, без флага — `maintenance: null`. Health check деплоя проходит и во время техобслуживания.
- **Обход только с loopback.** Запросы с `request.socket.remoteAddress` ∈ {`127.0.0.1`, `::1`, `::ffff:127.0.0.1`} работают как обычно. `X-Forwarded-For` не учитывается. Владелец проверяет живой сайт через `ssh -L 3002:127.0.0.1:3002 ubuntu@<VPS>` на `http://localhost:3002`. Caddy ходит в Node из docker-сети (`172.18.0.1`), поэтому публичные запросы обход не получают. Проба §1.6 проверяет это на проде.
- Это **заменяет** «исключение для запросов админа» из спеки 3.0. Публичный сайт не может узнать админа до загрузки HTML: токен лежит в localStorage, а не в cookie.

### 1.2 Страница `public/maintenance/`

- Самодостаточная: `index.html`, `maintenance.css`, `maintenance.js` внешними файлами (CSP без inline JS). Модулей приложения, `theme-boot.js` и `tokens.css` не подключает.
- Вид и три состояния — по прототипам 0.9.1 (`Maintenance`, `MaintenanceDown`, `MaintenanceDone`, мобайл и десктоп): плановые работы, сбой, готово. Без кнопки Telegram и без блока «что изменится».
- Палитры 0.9.1 (4 светлых и 4 тёмных) — в `maintenance.css`. Тема берётся из `gata-league-theme` в localStorage. Старые id тем 2.0 переводятся в ближайшую палитру по таблице соответствия. Та же таблица потом переходит в `src/core/theme.mjs` на этапе 4. Без кеша палитра по умолчанию выбирается по `prefers-color-scheme`.
- Тексты EN/RU — небольшой словарь внутри `maintenance.js`. Язык — из `gata-league-locale`, иначе по `navigator.language`.
- Раз в 30 секунд опрашивает `/api/health`. Когда `maintenance` становится `null`, показывает «Готово» и через 5 секунд перезагружает страницу.
- Шрифты Golos Text и Oswald (woff2, OFL) переезжают из `docs/redesign/handoff-0.9.1/design-system/fonts/` в `assets/fonts/` уже в этом релизе. Этап 4 использует их оттуда.

### 1.3 Клиент 2.x

`src/core/api.mjs`: на ответ `503` с кодом `MAINTENANCE` — один `location.reload()`. От цикла защищает метка в `sessionStorage`: не чаще раза в 30 секунд. После перезагрузки сервер отдаёт страницу техобслуживания, а она после работ перезагружает уже новую версию. Вкладки, открытые во время переезда, переходят сами.

### 1.4 Команды техобслуживания

`scripts/maintenance.mjs`:

- `npm run maintenance:on -- --kind planned --ends "2026-11-02T19:00+04:00"`;
- `npm run maintenance:off`;
- `npm run maintenance:status`.

Путь берётся так же, как у сервера (`server/config/env-file.mjs`). Файл пишется атомарно (временный файл → `rename`), значения проверяются. Нужны права root (`sudo -i`).

### 1.5 Дамп перед миграцией в деплое

- `scripts/backup-db.mjs` получает `--label premigrate`. Имя файла — `gata_league-premigrate-YYYYMMDD-HHMMSS.dump`. Регулярка ротации (`scripts/backup/rotation.mjs`, `^gata_league-\d{8}-\d{6}\.dump$`) такие файлы не трогает. Их удаляют вручную по чек-листу §6.4.
- `npm run deploy:migrate` (`scripts/deploy-migrate.mjs`):
  1. проверяет миграции (`migrationStatus`);
  2. если есть неприменённые, снимает дамп `premigrate`;
  3. только при успешном дампе применяет миграции.

  Если дамп не удался, команда завершается с ошибкой до изменения схемы. Если миграций нет, печатает `no pending migrations, backup skipped`. Логика решения — чистая функция с тестами.
- `.github/workflows/deploy.yml` вызывает `npm run deploy:migrate` вместо `npm run db:migrate`. Откат кода по health check не меняется.

### 1.6 Выпуск и проба на проде

- Версия 2.1.0, CHANGELOG, разделы в `DEPLOYMENT.md`: техобслуживание, обход через туннель, `deploy:migrate`. Тег `v2.1.0` — цель отката в день X.
- **Проба** (команды готовит Claude, выполняет владелец в тихое время):
  1. `maintenance:on --kind planned` на 2 минуты;
  2. проверить:
     - с телефона видна страница в своей палитре;
     - открытая заранее вкладка сама на неё перешла;
     - `/api/health` показывает флаг;
     - через туннель сайт работает;
     - лог деплоя содержит `no pending migrations, backup skipped`;
  3. `maintenance:off` → «Готово» → перезагрузка.
- Caddy **не трогаем**: он общий с соседним проектом, а в день X Node не выключается. 502 бывает только на секунды во время `pm2 restart`. Страница на случай полного падения Node — вне объёма (§8).

## 2. Оркестрация агентов

### 2.1 Ветки и слияния

- Этап ведётся в ветке `rd/NN-…` от свежей `redesign`, в отдельном worktree. Первым шагом агент проверяет `git rev-parse HEAD` против ожидаемой базы: при прошлом параллельном прогоне worktree поднимались на чужой ветке.
- Этапный PR вливается в `redesign` обычным merge commit (`gh pr merge --merge`). Коммиты по пунктам плана сохраняются.
- Фиксы из `main` Claude вливает в `redesign` сразу (`git merge main`), конфликты решаются в `redesign`.
- Конфликты в `src/i18n/en.json`, `ru.json`, `src/core/routes.mjs`, `scripts/check-budgets.json` и в чекбоксах плана механические. Их разрешает Claude при ребейзе второй из параллельных веток.

### 2.2 Конвейер этапа

1. **План этапа** (skill writing-plans) на основе плана 3.0, спеки 3.0, спецификации интерфейса 0.9.1 и `SCREENS.md`, с задачами по 2–5 минут.
2. **По каждой задаче** (skill subagent-driven-development):
   - агент-исполнитель (TDD);
   - ревьюер соответствия спеке;
   - ревьюер качества кода.

   Замечания исправляются до следующей задачи.
3. **Финальное ревью** всего этапа.
4. **Проверки:** `npm test && npm run check && npm run i18n:check && npm run build`, `npm run smoke` и `smoke:pre-match / smoke:friendly / smoke:post-match` для этапов с матчами, `PR-CHECKLIST.md`. CI с тестами в репозитории нет, поэтому вывод проверок прикладывается к PR.
5. **Скриншоты** встроенным браузером: 390 и 1440, светлая и одна тёмная палитра, все состояния экрана из `SCREENS.md`; выборочно 768 и 1024.
6. **PR в `redesign`** с выводом проверок и скриншотами → слияние → чекбоксы плана 3.0 → следующий этап.

### 2.3 Когда Claude останавливается

- Нужно продуктовое решение, которого нет в спеках.
- Прототипы противоречат друг другу.
- Контент и код расходятся в правиле (§0.11).

Останавливается только этот трек, второй продолжает. Между сессиями источник правды — чекбоксы плана 3.0 и состояние PR.

### 2.4 Цепочка PR и вехи

```
main      : П · релиз 2.1.0 (вливает владелец → деплой → проба §1.6)
redesign  : #10 план и спеки (+ правки §7)
          → 01 инструменты репетиции + перенос из PR #9
          → [02a данные → 02b match_events → 03 API] ∥ [04 токены и src/ui → 05 оболочка]
          → M1
          → 06 команды ∥ 11 справочник → 07a…07e состав ∥ 08 казна            → M2
          → 09a матчи и подготовка → 09b итоги → 09c вызовы ∥ 10 сезон         → M3
          → 12 админка                                                         → M4
          → 13 зачистка                                                        → M5
main      : PR redesign → main (вливает владелец в день X, §6)
```

| Веха | После этапов | Что получает владелец |
|---|---|---|
| M1 | 03, 05 | репетиция №1: миграции на копии боевых данных; новая оболочка, вход, настройки |
| M2 | 06, 07, 08, 11 | обзор команды, состав целиком, казна, справочник |
| M3 | 09, 10 | репетиция №2: полный товарищеский матч (подготовка → записи → итоги) и сквозной тест переходных состояний; вызовы, таблица |
| M4 | 12 | репетиция №3: функционально всё готово; список «команда → стадия → почему» и перенесённые погибшие на проверку |
| M5 | 13 | финальная репетиция на свежем дампе (§6.1), решение «go / no-go», дата дня X |

На каждой вехе — отчёт `docs/redesign/reports/Mn.md`: ссылки на PR, скриншоты, итог репетиции (только сводка), бюджеты, вопросы к владельцу и команда, чтобы поднять `redesign` у себя. Отчёты удаляются на этапе 13.

## 3. Генеральная репетиция на обезличенной копии

### 3.1 Инструменты (этап 01, в `redesign`)

Все три команды отказываются работать, если `DATABASE_URL` указывает не на локальную базу (как уже делают smoke-скрипты).

- **`npm run rehearsal:restore -- <дамп>`.** Одной командой:
  1. пересоздаёт базу `gata_rehearsal` в локальном docker-контейнере;
  2. разворачивает дамп (`pg_restore`);
  3. в одной транзакции обезличивает:
     - `users.password_hash` → `hashPassword(REHEARSAL_PASSWORD)` (`server/auth/session.mjs`), пароль — в локальном `.env`;
     - `users.telegram` → `@coach_N`;
     - `sessions` очищается.

  Логины, названия команд, составы и результаты остаются: они публичны на сайте, а по логину Claude входит под тренером.
- **`npm run rehearsal:check -- --before | --after`** снимает и сравнивает слепки в `output/rehearsal/`:
  - число строк по каждой таблице;
  - `roster::text` и `revision` каждой команды **не изменились** (§0.8 спеки 3.0);
  - результаты и очки таблицы сезона совпадают; TV не пересчитывается: миграции не меняют ни блоб, ни справочные данные, поэтому совпадение блоба означает совпадение TV;
  - после миграций:
    - распределение `stage` со списком «команда → стадия → почему»;
    - `preferences = {}` у всех пользователей;
    - перенесённые погибшие по командам;
  - инвентарь открытых состояний: начатые подготовки, начатые матчи без завершённых итогов, неподтверждённые счета, висящие вызовы;
  - время применения миграций.
- **`npm run rehearsal:transitions`** — сквозной тест переходных состояний (§3.3).

### 3.2 Порядок одной репетиции

1. **Владелец:** снимает дамп на VPS (`npm run backup:db`) и копирует его через `scp` в `~/gata-dumps/` (диск под FileVault, права `600`). Это та же процедура, что в день X.
2. **Claude:**
   1. `rehearsal:restore` → `rehearsal:check --before` → миграции кодом `redesign` → `rehearsal:check --after`;
   2. сервер 3.0 на этой базе → все smoke-сценарии;
   3. проход встроенным браузером под 4–5 реальными тренерами (разные расы; команда с погибшими и пропускающими; тренер с наибольшим числом матчей; админ) на 390 и 1440: обзор, состав, профиль, карьера по матчам (включая восстановленную из `match_post_applications`), казна, таблица, справочник, старые ссылки из списка редиректов;
   4. с M3 — полный товарищеский матч и `rehearsal:transitions`.
3. **Проверка отката:** код `v2.1.0` (отдельный worktree) на мигрированной базе → `/api/health` и `npm run smoke`. Это доказывает сценарий 1 из §4.2.
4. **Отчёт:** сводка в `docs/redesign/reports/Mn.md` (счётчики и «ок / не ок», без персональных данных), подробности — в `output/` (он в `.gitignore`).

Репетиции проходят на M1, M3, M4 и M5. На M5 используется свежий дамп за 1–2 дня до дня X.

### 3.3 Сквозной тест переходных состояний

На свежей репетиционной базе сервер `v2.1.0` (worktree, отдельный порт) через API создаёт:

- начатую подготовку (шаги 1–2);
- начатый матч (снимки составов);
- итоги, заполненные до шага «Игроки» включительно;
- предложенный, но не подтверждённый счёт;
- висящий вызов.

Затем сервер останавливается, применяются миграции, запускается 3.0, и скрипт доводит каждое состояние до конца через API 3.0. Проверки:

- подготовка продолжается с того же шага;
- итоги, начатые в 2.x, завершаются без `POST_TEAM_CHANGED`; SPP после матча = SPP до + статистика матча, **без двойного счёта**; записи матча получают `settled_at`; казна и очки верны;
- неподтверждённый счёт вносит админ;
- вызов принимается.

Если тест зелёный, начатые матчи с незавершёнными итогами в день X — предупреждение, если красный — блокер (§6.2).

### 3.4 Приватность

- Сырой дамп лежит только в `~/gata-dumps/`. Восстановление и обезличивание — одна команда, поэтому сырые данные не крутятся в работающей базе.
- Claude ничего из дампа не коммитит и никуда не отправляет.
- Через 14 дней после дня X дампы и база `gata_rehearsal` удаляются (§6.4).

## 4. Бэкапы и восстановление

### 4.1 Слои

| Слой | Что | Где | Когда | Хранение |
|---|---|---|---|---|
| Ночной (есть) | `pg_dump -Fc` с самопроверкой | VPS, `/var/backups/bloodbowl-league` | 04:00 UTC ежедневно | 7 последних |
| Перед миграцией (2.1.0) | тот же дамп, `gata_league-premigrate-…` | там же | сам, при деплое с неприменёнными миграциями | вне ротации, удаляется по §6.4 |
| День X | ручной дамп + `sha256sum` + копия на Mac со сверкой суммы | VPS + `~/gata-dumps/` | шаг T+2 runbook | 14 дней после дня X |
| Код | теги `v2.1.0`, `v3.0.0` | GitHub | при релизах | всегда |

Конфиги сервера (`.env`, systemd, Caddy, pm2) в день X не меняются, отдельный бэкап им не нужен. Данные в браузерах тренеров бэкапа не требуют (§5.4).

**Точка невозврата — `maintenance:off` в день X.** До неё тренеры ничего не записали в 3.0, и любой откат делается кодом. После неё — только исправления вперёд.

### 4.2 Сценарии восстановления

1. **3.0 ведёт себя плохо, техобслуживание ещё включено.**
   - Код откатывается на `v2.1.0`, `pm2 restart`, база **не восстанавливается**.
   - Миграции аддитивные; что 2.1.0 работает на мигрированной схеме, проверяет каждая репетиция (§3.2, шаг 3).
   - Техобслуживание выключается уже на 2.1.0, переезд переносится.
2. **Миграция упала на середине.**
   - Каждый файл применяется в своей транзакции, база остаётся на последней успешной миграции.
   - 3.0 не стартует (`assertMigrationsApplied`), health check деплоя проваливается, workflow откатывает код. 2.1.0 стартует: лишние таблицы ему не мешают.
   - Восстановление не нужно. Причину разбираем на репетиционной копии, чиним новой миграцией.
3. **Порча данных обнаружена после точки невозврата.**
   - По умолчанию — **точечный ремонт**: дамп дня X разворачивается рядом, в `gata_league_recover`, и переносятся только пострадавшие строки.
   - Полное восстановление — только при катастрофе и в первые часы:
     1. `maintenance:on`;
     2. `pm2 stop bloodbowl-league`;
     3. `pg_restore --clean --if-exists` дампа дня X;
     4. код `v2.1.0`: в восстановленной базе нет миграций 009–015, и 3.0 на ней не стартует;
     5. `pm2 start`.
   - Всё, что тренеры записали после переезда, при этом теряется. Это решение владельца.

Каждая репетиция — реальное восстановление боевого дампа. К дню X процедура проверена минимум четыре раза. Это закрывает пункт `DEPLOYMENT.md` «не проверено, что дамп, снятый на сервере, разворачивается».

## 5. Миграция данных и файлов

### 5.1 База данных

**Принцип: миграции только добавляют.** Ни одна существующая строка не удаляется и не перезаписывается, текущий сезон продолжается.

| Данные | Таблицы | В 3.0 |
|---|---|---|
| Сезон, туры, пары, счета, очки | `seasons`, `season_rounds`, `season_pairings`, `season_entries` | без изменений, очки сверяются репетицией |
| Составы: SPP, прокачки, травмы, казна, пропуски | roster-блоб в `saved_teams` | без изменений, побайтно |
| Матчи, сыгранные через итоги на сайте | `match_post_games`, `match_post_applications` | без изменений, из них строится карьера по матчам |
| Подготовки, снимки, траты на индьюсменты | `match_preparations`, `match_roster_snapshots`, `match_treasury_spends` | без изменений, начатая подготовка продолжается |
| Вызовы | `friendly_challenges` | без изменений |

- **`009_team_stage.sql`.** Колонка с `DEFAULT 'active'`, затем в той же миграции `draft` ставится командам, у которых нет ни неотозванной заявки в текущий сезон (`seasons.status = 'active'`; если активного сезона нет, остаётся только второе условие), ни сыгранного матча (лигового или товарищеского, с `result_status = 'confirmed'` или строкой в `match_post_applications`). `activated_at` у команд, ставших `active` миграцией, остаётся `NULL` («до 3.0»).
- **`011_fallen_players.sql`** — только таблица, как в спеке 3.0.
- **`015_backfill_fallen_players.sql`** — перенос погибших:
  - для каждой строки `match_post_applications` берутся игроки, у которых в `match_post_games.state` этой стороны травма `dead`, `gamesPlayed` этой стороны в состоянии не меньше трёх (защита новичков, как в `effectiveInjury`: меньше трёх матчей — `dead` становится Badly Hurt, хотя в состоянии код остаётся `dead`; без целого `gamesPlayed` не переносится никто) и которых нет в `after_roster`;
  - в `team_fallen_players` пишутся снимок игрока из `before_roster`, `pairing_id`, `died_at = created_at` строки, причина `NULL` (в состояниях 2.x её нет), `recorded_by` `NULL`, `from_match = true` (колонку добавляет та же миграция, §3.3 спеки 3.0);
  - повторный запуск ничего не дублирует (`NOT EXISTS` по `saved_team_id, pairing_id, player->>'id'`).

  Это гибель «из матча»: тренер её не отменяет (`FALLEN_FROM_MATCH`).
- **Погибших, удалённых вручную без итогов,** восстановить из БД нельзя: истории блобов нет. Админ дописывает их: `POST /api/admin/teams/:id/fallen {player: {name, position, number?}, cause, pairingId?, diedAt?}`, этап 12. Отчёт репетиции M4 со списком перенесённых по командам владелец сверяет со своей памятью.
- **Пропуски.** Игроки, которые сейчас пропускают матч, сохраняют `skipNextGame`, поле `absence` у них `null` (блобы не переписываются). Интерфейс показывает «Пропускает матч» без причины.
- **Новые таблицы** (`team_ledger`, `match_events`, `dice_rolls`) начинаются пустыми: этих данных до 3.0 не существует. Казна остаётся в блобе. Подпись «История ведётся с …» берёт `applied_at` миграции `010` из `schema_migrations`.
- `013_user_preferences.sql`: у всех `preferences = {}`.

## 8. Что не делаем

- Не трогаем общий Caddy и не делаем страницу на случай полного падения Node: это мониторинг, а не переезд.
- Не делаем снапшот VPS и холодную копию тома Postgres (решение владельца, §0.5).
- Не применяем миграции к проду заранее (подход B отклонён): файлы миграций замораживались бы до конца работы, а выигрыш — секунды.
- Не делаем blue-green (подход C): общий Caddy и расхождение двух баз.
- Не заполняем задним числом журнал казны и записи матча и не переписываем блобы ради `absence`.
- Не импортируем старый черновик билдера.
- Не запускаем smoke-сценарии против боевой базы: они создают одноразовые данные и отказываются работать не с локальной базой.

## 9. Риски

| Риск | Чем закрыт |
|---|---|
| Миграция ломается на реальных данных | 4 репетиции на копии боевой базы, `rehearsal:check` |
| Двойной счёт SPP у матча, начатого в 2.x | сквозной тест §3.3; при красном тесте такие матчи — блокер окна |
| Откат после переезда теряет данные | точка невозврата `maintenance:off`; до неё откат кодом, после — исправления вперёд или точечный ремонт |
| Деплой меняет схему без бэкапа | `deploy:migrate`: без дампа миграции не применяются |
| Тренеры видят полусломанный сайт во время работ | режим техобслуживания из 2.1.0, проверен на проде пробой §1.6 |
| Обход техобслуживания достаётся публичным запросам | обход только по `remoteAddress` loopback; проба проверяет, что с телефона видна страница |
| Пропадут погибшие этого сезона | `015` переносит их из итогов, остальных дописывает админ, отчёт M4 сверяет владелец |
| Ошибка в стадиях команд | список «команда → стадия → почему» на M4 и M5 до дня X |
| Агенты расходятся в виде экранов | `src/ui/*` готов до экранных этапов, не больше двух этапов одновременно, вехи с вашей проверкой |
| Дамп с персональными данными утечёт с Mac | FileVault, права `600`, обезличивание в той же команде, удаление через 14 дней |
