# Ежедневный ночной бэкап базы

**Дата:** 2026-08-22
**Статус:** спека согласована, реализация не начата
**Контекст:** боевой Postgres 16 в Docker (`gata-league-postgres`) на VPS `51.81.86.51`,
приложение под pm2, деплой — GitHub Actions по пушу в `main`.

---

## 1. Задача

Раз в сутки снимать дамп базы `gata_league` и хранить семь последних. Сейчас бэкапов нет
вообще: единственная копия данных — том `gata_postgres_data`. Любая порча данных
(ошибочный `DELETE`, сломанная миграция, случайный `docker compose down -v`) необратима.

## 2. Что этот бэкап закрывает, а что нет

| Сценарий | Закрыт |
|---|---|
| Удалили/испортили данные, заметили в течение недели | да |
| Сломали схему миграцией | да |
| Снесли том `gata_postgres_data` | да |
| VPS потерян, взломан или недоступен | **нет** |
| Порчу заметили позже чем через 7 дней | **нет** |
| Утечка дампа при компрометации хоста | **нет** (дампы не шифруются) |

Хранение только на самом VPS выбрано сознательно: offsite-копия требует внешнего аккаунта
и второго набора ключей в `/etc/bloodbowl-league/.env` — ровно того, от чего проект ушёл
после инцидента 2026-08-22. Это осознанная граница, а не недосмотр; см. раздел 9.

## 3. Принятые решения

| Решение | Выбрано | Почему не альтернатива |
|---|---|---|
| Место хранения | только VPS, `/var/backups/bloodbowl-league` | offsite — новые секреты на сервере; ручное скачивание — зависит от дисциплины |
| Формат | `pg_dump -Fc` (custom) | plain SQL хуже для частичного восстановления; `pg_dumpall` кладёт на диск хэши паролей ролей |
| Запуск | systemd timer | cron молча теряет пропущенные запуски и требует ручного логирования; сайдкар в compose деплой не перезапускает |
| Контроль | самопроверка дампа + команда статуса | Telegram требует бот-токен в env; статус в админке — новый UI и ключи i18n |
| Ротация | хранить **7 последних файлов** | `find -mtime +7 -delete` при сломанном таймере оставляет ноль бэкапов |
| Язык скрипта | Node (`scripts/*.mjs`) | bash не даёт покрыть тестом логику, которая удаляет файлы |

## 4. Размещение файлов

```
репозиторий (приезжает деплоем автоматически)
  scripts/backup-db.mjs                       снять дамп, проверить, ротировать
  scripts/backup-status.mjs                   показать состояние бэкапов
  scripts/backup/rotation.mjs                 чистая функция выбора файлов на удаление
  deploy/systemd/bloodbowl-backup.service
  deploy/systemd/bloodbowl-backup.timer
  test/backup-rotation.test.mjs

сервер (ставится один раз руками)
  /etc/systemd/system/bloodbowl-backup.service  симлинк на deploy/systemd/…
  /etc/systemd/system/bloodbowl-backup.timer    симлинк на deploy/systemd/…
  /var/backups/bloodbowl-league/                root:root, 0700
```

Дампы лежат **вне** `/opt/bloodbowl-league`. Эта директория раздаётся по HTTP и один раз
уже отдала `.env` всем желающим. Дамп базы — секрет того же класса: логины, хэши паролей,
телеграм-контакты. Директория `0700`, файлы `0600`, владелец `root`.

Юниты — симлинками в репозиторий, чтобы правка приезжала деплоем и не расходилась с git.
Оговорка та же, что уже записана в DEPLOYMENT.md про `docker-compose.yml`: деплой не
делает `systemctl daemon-reload`, поэтому изменение юнита доезжает до systemd только
после ручного шага. Это должно быть написано в документации явно.

## 5. Что делает `scripts/backup-db.mjs`

Порядок шагов важен: файл получает финальное имя только после того, как проверен.

1. Читает `POSTGRES_DB` и `POSTGRES_USER` через существующий
   `server/config/env-file.mjs` (`BLOODBOWL_ENV_FILE` → `/etc/bloodbowl-league/.env` →
   `.env` в корне репозитория). Свой парсер env не пишем.
2. `docker exec gata-league-postgres pg_dump -Fc -U <user> -d <db>`, вывод пишется в
   `gata_league-YYYYMMDD-HHMMSS.dump.partial` (метка времени в UTC).
3. Проверяет: код возврата `pg_dump` — ноль; размер файла больше нуля;
   `pg_restore --list` по файлу отрабатывает без ошибки.
4. Только после успеха — `rename` в `…​.dump`. Недоснятый дамп никогда не выглядит как
   готовый и не попадает в ротацию.
5. Ротация: удаляются все `*.dump`, кроме семи свежайших. Свежесть определяется меткой
   времени в имени файла — она в UTC и фиксированной ширины, поэтому лексикографическая
   сортировка совпадает с хронологической и не зависит от `mtime`, который может быть
   переписан копированием. Файлы, не подходящие под шаблон имени, не трогаются вообще. `*.partial` старше суток удаляются как мусор.
6. Любая осечка — ненулевой код возврата процесса, systemd помечает запуск `failed`.

**Аутентификация `pg_dump`.** В образе `postgres:16` локальные подключения внутри
контейнера, как правило, настроены на `trust`, и пароль не нужен — это предпочтительный
вариант, потому что не кладёт секрет ни в аргументы, ни в окружение. Проверяется на
сервере первым шагом реализации:

```bash
docker exec gata-league-postgres pg_dump -U gata_admin -d gata_league --schema-only -f /dev/null && echo "без пароля работает"
```

Если не работает — пароль передаётся через окружение процесса (`docker exec -e`), а не
аргументом командной строки, чтобы он не был виден в `ps` на хосте. Выбранный вариант
фиксируется в комментарии к скрипту.

## 6. Расписание

`deploy/systemd/bloodbowl-backup.timer`:

- `OnCalendar=*-*-* 04:00:00 UTC` — фиксированный UTC, чтобы перевод часов не сдвигал и
  не дублировал запуск;
- `Persistent=true` — запуск, пропущенный из-за выключенного сервера, догоняется при
  старте;
- `RandomizedDelaySec=300`.

Сервис — `Type=oneshot`, вывод уходит в journal под `bloodbowl-backup`.

## 7. Контроль состояния

`npm run backup:status` (`scripts/backup-status.mjs`) печатает:

- количество дампов и суммарный занятый объём;
- имя, размер и возраст свежайшего дампа;
- результат последнего запуска таймера (из `systemctl show bloodbowl-backup.service`);
- время следующего запуска.

Команда завершается ненулевым кодом, если свежайшему дампу больше 48 часов или последний
запуск сервиса был неуспешным. Один вызов отвечает на вопрос «всё ли в порядке», не
требуя чтения журналов.

## 8. Восстановление

Бэкап, который ни разу не разворачивали, — не бэкап, а надежда. В объём работы входит:

1. Раздел «Восстановление из бэкапа» в `DEPLOYMENT.md`: точные команды, включая остановку
   `pm2` перед накатом на боевую базу и проверку после.
2. **Однократная репетиция на сервере** — обязательная часть приёмки, не опция:
   развернуть свежий дамп в отдельную базу `gata_league_restore_check`, сравнить число
   строк в `users` и в таблицах команд с боевой базой, удалить проверочную базу, записать
   результат в `DEPLOYMENT.md` с датой.

## 9. Что сознательно не делается

Ни один из пунктов ниже не входит в работу; каждый добавляет движущихся частей больше,
чем защиты, на текущем масштабе проекта:

- offsite-копия (S3, Backblaze, второй хост) — отложена осознанно, см. раздел 2;
- шифрование дампов на диске;
- PITR / архив WAL;
- уведомления (Telegram, почта);
- ежедневные + еженедельные бэкапы с разной глубиной хранения;
- изменение `docker-compose.yml` — бэкап не требует ни новых томов, ни сайдкаров.

## 10. Тесты и приёмка

**Тесты** (`npm test`, `node --test`): `test/backup-rotation.test.mjs` покрывает чистую
функцию выбора файлов на удаление на временной директории:

- файлов меньше семи — не удаляется ничего;
- файлов больше семи — остаются ровно семь свежайших;
- посторонние файлы в директории не удаляются;
- `.partial` не считается дампом и не попадает в число семи;
- `.partial` старше суток удаляется, свежий — нет.

**Приёмка** — каждый пункт проверен на сервере, а не предположен:

| Критерий | Как подтверждается |
|---|---|
| `npm test` зелёный | вывод `node --test` |
| Ручной запуск снимает дамп | `systemctl start bloodbowl-backup.service`, файл появился, `pg_restore --list` читается |
| Таймер активен и запланирован | `systemctl list-timers bloodbowl-backup` |
| Ночной запуск отработал сам | на следующие сутки: свежий дамп с ночной меткой времени, `systemctl status` без ошибок |
| Ротация работает | после ≥8 запусков (можно ускорить ручными) в директории ровно 7 файлов |
| Права закрыты | `stat` даёт `0700` на директории и `0600` на файлах, владелец `root` |
| Дампы не раздаются по HTTP | `curl` по пути дампа → `404`; проверка, что `/var/backups` вне веб-корня |
| Восстановление проверено | репетиция из раздела 8 выполнена, результат записан в `DEPLOYMENT.md` |
| `backup:status` полезен | падает с ненулевым кодом на искусственно устаревшем наборе дампов |
| Документация | разделы про бэкап и восстановление в `DEPLOYMENT.md`, включая оговорку про `daemon-reload` |

## 11. Открытые вопросы, решаемые при реализации

1. Нужен ли пароль для `pg_dump` внутри контейнера (раздел 5) — проверяется командой
   оттуда же.
2. Реальный размер дампа и свободное место на `/var` — измеряется на сервере перед
   установкой таймера. Ожидание: единицы мегабайт на семь файлов; если окажется иначе,
   решение о глубине хранения пересматривается и фиксируется здесь.
