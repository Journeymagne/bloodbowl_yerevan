## 3. Проблема A — способ рендеринга (P1)

Единый паттерн во всём приложении: собрать HTML-строку → `view.innerHTML = ...` → заново найти узлы через `querySelector` → заново навесить обработчики.

**Следствия, воспроизводимые в проде:**

1. **Любое изменение — полная перерисовка экрана.** В редакторе ростера `rerender()` (`src/app.js:5321`) вызывает `renderSavedRoster(teamId, false)`, который переписывает `view.innerHTML` целиком (`4993-5014`). Теряется фокус в поле ввода, позиция скролла, раскрытые карточки игроков (их приходится восстанавливать отдельным глобальным состоянием `state.savedRosterUi.expandedPlayers`, `src/app.js:38-39`).
2. **Обходные пути уже вросли в код.** В `wireSavedPlayerEditors` (`5556-5571`) обработчик ввода SPP вручную патчит четыре разных узла (`data-player-spp-total`, `data-player-available-spp`, `data-player-next-advancement`, `data-total-spp-display`), чтобы не вызывать полную перерисовку. Это ручная имитация реактивности в одном месте из десятков.
3. **Двойной DOM для мобильных.** Каждая таблица рендерится дважды: десктопная `<table>` и мобильный список карточек — оба всегда в DOM, переключаются CSS. Пример: `renderSavedPlayerList` (`6256-6299`) рендерит и `renderSavedPlayerRow` (73 строки), и `renderSavedPlayerCard` (94 строки) для каждого игрока. То же для `renderSavedTeamRow`/`renderSavedTeamCard`, `renderBuilderPlayerRow`/`renderBuilderPlayerCard`, `renderTeamRosterMobile`, `renderReferenceTableMobile`, `renderSkillTableMobile`. Каждая правка логики строки требует двух одинаковых правок.
4. **Экранирование — по соглашению, а не по устройству.** `escapeHtml` вызывается вручную. Сейчас проверка показала, что критичные точки закрыты (`renderHeader:1965`, `renderOption:2162`), но одна забытая обёртка в 7,5 тыс. строк шаблонов даёт stored XSS, а токен сессии лежит в `localStorage` (`src/app.js:981`) и будет украден.
5. **Таблица ростера на 20 колонок** (`renderSavedPlayerList:6266-6285`) — предел того, что помещается в таблицу; поэтому и понадобился параллельный мобильный рендер.

## 4. Проблема B — организация информации (P2, местами P1)

**4.1. Три независимых источника контента.**

- `content/Gata/` + `content/Gata-ru/` → `scripts/build-data.mjs` → `public/data.<locale>.json` (правила, команды, скиллы, звёзды).
- `src/i18n/{en,ru}.json` — строки интерфейса.
- `overviewCards` / `overviewCardsRu` в `src/app.js:339-956` — **618 строк текста правил лиги, вшитых в код на двух языках**: кодекс поведения, общие правила, бюджет, выкуп команды, штрафы. Редактор лиги не может их править, они не проходят через `npm run i18n:check`, и они дублируют то, что уже есть в контент-хранилище.

**4.2. `data.json` дублирует сам себя.** Сборщик пишет каждую страницу в `pages` и ещё раз — в её коллекцию (`teams`, `skills`, `traits`, `starPlayers`, `inducements`, `rules`, `otherPages`). Проверено: 276 из 292 объектов присутствуют дважды, побайтово идентичные. Плюс каждая страница несёт три представления одного текста: `body` (markdown, 214 КБ), `html` (308 КБ), `text` (194 КБ) — `scripts/build-data.mjs:686,729-730`. Итог: 1,67 МБ, из которых полезных ~50 %; всё это грузится и парсится при первом открытии и полностью перезагружается при смене языка.

**4.3. Мёртвые фильтры.** `state.teamFilters` и `state.starFilters` (`src/app.js:5-14`) живы, но `renderTeamFilters` (`2165`), `renderStarFilters` (`2231`), `isTeamVisible` (`1906`), `rowCostRange` (`2332`) недостижимы — UI фильтров когда-то убрали, состояние и хелперы остались. На экране команд остался только глобальный поиск.

**4.4. Навигация.** 12 пунктов одного уровня смешивают три разные задачи: справочник (References/Inducements/Skills/Traits/Star Players/Team's Rules), личную игру (Builder/My Teams/My Games/Season) и администрирование. Гость видит четыре пункта, каждый из которых отвечает «войдите». Названия пересекаются: «References» и «Team's Rules» — обе про правила; «Team's Rules» на деле каталог рас.

**4.5. Сезон закрыт от гостей.** `GET /api/season` требует авторизации (`server/server.mjs:1723-1726`), поэтому таблица, расписание и результаты лиги невидимы без аккаунта. Для публичного сайта лиги это перевёрнутая логика.

**5.2. Две несовместимые экономики.** В билдере действует жёсткий бюджет 600k: кнопки просто молча не работают при превышении (`wireBuilder:7128`, `7160`, `7173` — `return` без какого-либо сообщения пользователю). В редакторе сохранённого ростера бюджета нет — есть казна (`treasury`), которую покупки уменьшают через `applyPaidStaffChange:7026`, и она может уйти в минус без предупреждения. При этом `calculateRosterCosts:7068` всё равно считает `remaining: 600 - total` даже для развитой команды в середине сезона, где эта цифра бессмысленна.

**5.3. Бюджет и правила зашиты в код.** `600` — 21 вхождение; лимиты состава `7` и `11` — `rosterWarnings:7078-7079`; стоимости персонала — `builderStaffCosts:259`; стоимость скилла 20/40 — `skillModCost:1800`; стоимость статов 10/20/30/40/50 — `advancementStatCosts:307`; элит-комбо +15k — `eliteComboCost:1805`; ранги и цены прокачки — `advancementRanks:291`. Те же числа отдельно записаны текстом в `content/Gata/` и в `overviewCards`. Любое изменение правил лиги требует синхронной правки в трёх местах, и ничто не проверяет расхождение.

**5.4. Мёртвый код — 41 функция, ~615 строк.** Проверено анализом достижимости от `init()`:

`optionLabel`, `emptyRosterSlots`, `normalizeSlot`, `ensureRosterSlots`, `syncRosterCountsFromSlots`, `allRosterRows`, `allRowSkills`, `allRowTags`, `allRowCosts`, `isTeamVisible`, `renderSimpleCard`, `renderTeamFilters`, `renderStarFilters`, `rowCostRange`, `renderPublicTeamSummary`, `seasonEntryMap`, `renderRosterAddon`, `rowCountInSlots`, `rowAvailableForSlot`, `addableRowsForSlots`, `renderRosterSlot`, `renderSlotPlayerEditor`, `renderRosterStepper`, `wireSlotPlayerEditors`, `renderBuilderIdentity`, `renderBuilderPurchases`, `renderBuilderSummary`, `renderPlainSkillPills`, `renderAddon`, `renderBuilderRow`, `selectedBuilderRows`, `selectedRosterRows`, `selectedBuilderPlayers`, `ensurePlayerEdit`, `statValueForDisplay`, `availableSkillsForRow`, `renderBuilderSummaryRoster`, `renderEditableRosterPlayers`, `renderEditablePlayer`, `renderStepper`, `wirePlayerEditors`.

Это два полностью заброшенных поколения редактора игрока (слоты и `playerEdits`), которые всё ещё влияют на формат данных — см. раздел 6.

**5.5. Предупреждения билдера не переведены.** `rosterWarnings:7078-7086` возвращает захардкоженные английские строки («A Sevens roster usually needs at least 7 players.», `` `${row.position}: minimum is ${min}.` ``) в обход `t()`. Это прямое нарушение правила из `CLAUDE.md` и единственная такая дыра в приложении — и она ровно в рефакторимой зоне.

**5.6. Прокачка ведётся в двух не связанных между собой учётах.** `player.advancements` тратит SPP (`playerAdvancementSpent:2682`), а фактические скиллы и статы добавляются отдельными кнопками и стоят золота (`playerAdjustmentCost:1817`). Ничто не связывает «взял прокачку» и «получил скилл»: можно иметь шесть прокачек без единого скилла или шесть скиллов без прокачек. Плюс добавление прокачки не проверяет наличие SPP — `wireSavedPlayerEditors:5630-5636` проверяет только `if (!cost) return`, поэтому доступный SPP уходит в минус.

**5.7. Мелкие, но заметные дефекты билдера.**

- Смена расы в билдере (`wireBuilder:7092-7096`) и в сохранённом ростере (`wireSavedRoster:5333-5342`, `draft.players = []`) стирает весь ростер **без подтверждения**, а в сохранённом ростере это ещё и немедленно автосохраняется.
- `emptyBuilderState:1423` не содержит поля `selectedLeague`, хотя оно есть в исходном `state.builder:59` — после `resetBuilderForTeam` поле становится `undefined` и держится только на `|| ""` в четырёх местах.

- `buildRosterText(team)` объявлена с одним параметром, а вызывается с двумя (`copyRoster:7311`).
- `apiRequest:1010` — бессмысленный псевдоним `authRequest`.

## 6. Проблема D — модель ростера: три поколения в одном JSONB (P0 для данных)

В колонке `saved_teams.roster` (JSONB, без схемы и без версии) сосуществуют три поколения формата:

1. **Поколение 1:** `roster` — счётчики `{ rowIndex: count }` + `playerEdits` — правки по ключу `` `${rowIndex}-${copyIndex}` `` (`playerKey:6776`).
2. **Поколение 2:** `slots` — массив фиксированной длины `rosterSlotCount = 14` (`src/app.js:289`).
3. **Поколение 3 (текущее):** `players[]` — массив объектов с `id`, `rowIndex`, `statMods`, `extraSkills`, `favouredSkills`, `spp`, `advancements`.

`playersFromLegacyRoster:1657` мигрирует старое в новое **при каждом чтении**, `ensureDraftPlayers:1692` удаляет `slots` из черновика, но:

- `builderPayload:1452` и `normalizeSavedRoster:1478` продолжают писать в базу `roster` и `playerEdits` навсегда, хотя `roster` — производные счётчики (`syncRosterCountsFromPlayers:1699`), а `playerEdits` читается только мёртвым кодом;
- миграция никогда не фиксируется отдельно — если завтра сломается `playersFromLegacyRoster`, старые команды превратятся в пустые ростеры;
- форма черновика описана **четырьмя** несогласованными местами: `state.builder` (`src/app.js:55-76`), `emptyBuilderState:1423`, `builderPayload:1452`, `normalizeSavedRoster:1478`;
- логотип хранится дважды: в колонке `logo_data` и внутри блоба; сервер вырезает его из блоба рекурсивно при каждом чтении и записи (`stripEmbeddedLogoData:126`, `serializeRosterForStorage:145`), а клиент кладёт обратно.

### 6.1. Решено владельцем 2026-08-19: поддержка старых форматов удалена

Поколения 1 и 2 больше не читаются. Владелец лиги подтвердил, что все сохранённые команды давно живут в текущем формате, поэтому вместо «мигрируем при каждом чтении, а потом однократно в базе» выбран более короткий путь — просто перестать поддерживать старое.

Что это меняет по сравнению с первоначальным замыслом:

- **Задача 4 больше не содержит миграции данных.** Пункт про `scripts/migrate-rosters.mjs`, который переписывал бы каждую строку `saved_teams.roster`, снят. Вместе с ним уходит единственная необратимая операция во всём плане — и, соответственно, требование снять дамп базы именно ради неё.
- **Появился предохранитель:** `scripts/check-roster-shapes.mjs` спрашивает у живой базы, есть ли хоть одна команда, у которой нет `players[]`, но есть `slots` или `playerEdits`. Такая команда после удаления читалась бы как пустой ростер. Скрипт запускается **до** выката и возвращает ненулевой код, если такие строки нашлись.
- Схема данных упростилась: из черновика ушли `playerEdits` и `slots`, из кода — 43 недостижимые функции (два заброшенных поколения редактора игрока целиком). `src/app.js` уменьшился с 7479 до 6154 строк.
- Остатки старых ключей в уже сохранённых блобах безвредны — приложение их не читает, и они исчезнут при первом же сохранении команды.

Отдельно: регулярных бэкапов базы в проекте нет вообще (ни `pg_dump` по расписанию, ни бэкап-сервиса в `docker-compose.yml`, ни упоминания в `DEPLOYMENT.md`). Это не связано с миграцией и остаётся открытым вопросом само по себе.

| 5 | Админ правит чужой ростер | тот же экран, `savedTeam._saveEndpoint` | `PATCH /api/admin/teams/:id` | весь блоб целиком |
| 6 | Админ создаёт команду игроку | `renderAdminCreateTeamForUserPanel:3534` | `POST /api/admin/users/:id/teams` | стартовый ростер |
| 7 | Админ создаёт команду в сезоне | `makeSeasonStarterRoster:4163` (**ростер собирается на клиенте**) | `POST /api/season/admin/create-team` | пустой стартовый ростер |
| 8 | Импорт из XLSX | `scripts/prepare-team-import.py` → `.team-import.json` → `POST /api/admin/import-users` | обход обычного пути |
| 9 | Экспорт | `copyRoster:7310` / `copySavedRoster:5800` | — | только текст в буфер обмена, файла нет, импорта обратно нет |
| 10 | Удаление | `deleteSavedTeam:3299` | `DELETE /api/teams/:id` | каскадом сносит участие в сезоне — см. 7.6 |

Семь путей записи ростера, три из которых обходят клиентскую логику целиком. Сервер не валидирует ни один.

### 7.2. P0: гонка «отсоединённый черновик» — потеря правок

Точный сценарий воспроизведения:

1. `renderSavedRoster:4981` создаёт черновик: `const draft = normalizeSavedRoster(savedTeam)`, при этом `normalizeSavedRoster:1505` присваивает `savedTeam.roster = draft` — UI и объект команды указывают на один объект `D1`.
2. Пользователь правит имя игрока → обработчик (`wireSavedPlayerEditors:5529`) мутирует `D1.players[i].name` и вызывает `autosave()`. Перерисовки нет.
3. Через 450 мс `runSavedRosterAutosave:5740` строит `D2` из `savedTeam.roster` и вызывает `saveSavedRoster`.
4. Ответ сервера: `Object.assign(savedTeam, result.team)` (`src/app.js:5773`) заменяет `savedTeam.roster` на **новый объект `S1`**, распарсенный из ответа. UI при этом продолжает держать ссылки на `D1`.
5. Пользователь правит дальше (имя, номер, SPP, флаг Nigling) — мутируется `D1`, который больше никем не читается.
6. Следующее автосохранение читает `savedTeam.roster === S1` и отправляет на сервер **версию без правок шага 5**. На экране правки видны, в базе их нет. После F5 они исчезают.

Уязвимые обработчики — те, что не вызывают ни `rerender()`, ни `updateSavedRosterFields()`: имя игрока (`5529`), номер (`5533`), Nigling (`5541`), ручной ввод SPP (`5556`). Именно ими пользуются чаще всего при заполнении ростера после матча.

### 7.3. P0: отсутствие оптимистичной блокировки

`PATCH /api/teams/:id` (`server/server.mjs:1935`) и `PATCH /api/admin/teams/:id` (`1568`) перезаписывают весь блоб без сверки версии. Последствия:

- админ и владелец, открывшие один ростер, затирают правки друг друга молча;
- две вкладки одного пользователя — то же самое;
- «сохранить» в старой вкладке откатывает час работы в новой.

Ни `updated_at`, ни ревизия клиенту не проверяются; в базе нет ни `revision`, ни истории.

### 7.4. P0: сервер не валидирует ростер

`POST/PATCH /api/teams` проверяют только непустое имя, непустой `baseTeamSlug` и размер логотипа (`server/server.mjs:1907-1913`, `1941-1947`). Сам `roster` принимается как произвольный JSON. Значит, любой пользователь через devtools или curl может сохранить команду с 30 игроками, отрицательной казной, чужими скиллами, статами +10 и произвольным SPP — и она попадёт в сезон. Для соревновательной лиги это дыра в целостности, а не только «валидация UI».

Дополнительно `readJson:417` читает тело запроса **без ограничения размера** — любой клиент может исчерпать память процесса.

### 7.5. P1: автосохранение без страховки

- Дебаунс 450 мс, без очереди: при быстрых правках запросы могут прийти на сервер не в том порядке; защита есть только на применение ответа (`options.revision`), но не на порядок записи.
- При ошибке — только текст статуса «autosave failed» (`saveSavedRoster:5793`), без повтора, без сохранения в локальное хранилище и без блокировки ухода со страницы. `beforeunload`, `navigator.onLine`, `AbortController`, `sendBeacon` в коде отсутствуют (проверено).
- Истёкшая сессия (401) не отличается от прочих ошибок: пользователь продолжает редактировать «в пустоту».
- В каждом сохранении отправляется весь блоб вместе с логотипом (`saveSavedRoster:5756-5764` — `draft.logoData` оптимизируется до 512 px/JPEG, но всё равно уезжает при каждом нажатии).

### 7.6. P0: удаление команды стирает историю сезона

`season_entries.saved_team_id` → `ON DELETE CASCADE` (`server/init.sql:53`), `season_pairings.home_entry_id/away_entry_id` → `ON DELETE CASCADE` (`init.sql:83-84`). Значит, удаление сохранённой команды удаляет её участие в сезоне и **все матчи с её участием, включая результаты соперников**. Кнопка удаления доступна прямо из редактора ростера (`wireSavedRoster:5427`) и подтверждается обычным `confirm()`.

### 7.7. P1: `init.sql` выполняется при каждом старте

`ensureSchema:337` прогоняет весь `server/init.sql` на каждом запуске, а этот файл содержит не только `CREATE TABLE IF NOT EXISTS`, но и правящие данные `UPDATE`: например `UPDATE season_pairings SET result_status = 'confirmed' ... WHERE home_points IS NOT NULL` (`init.sql:145-147`) и перевод раундов в `started` (`init.sql:154-161`). Любой рестарт процесса (в том числе штатный `pm2 restart` в деплое) заново подтверждает результаты, которые администратор мог вручную вернуть в `pending`.

## 8. Проблема F — ростер в процессе игры (P0 для лиги)

Сейчас связи между игрой и ростером нет вообще.

- Игра (`season_pairings`) хранит только тачдауны, кэжуалти и статус подтверждения. Экран игры (`renderGamePage:4077`) показывает логотипы, счёт и форму результата.
- `season_entries` ссылается на **живую** запись `saved_teams`. Ростер редактируется в любой момент, в том числе во время идущего раунда: старт раунда (`startSeasonRound:1248`) меняет только статусы раундов и `current_round`, никакой фиксации составов не делает.
- Следовательно: невозможно узнать, каким составом игрался матч 3-го тура; невозможно доказать, что соперник не докупил игрока после жеребьёвки; невозможно построить историю развития команды.
- Постматчевое обновление (SPP, травмы, смерть игрока, доход, найм) полностью ручное и никак не привязано к игре: игрок сам открывает `#/my-teams/:id` и накликивает счётчики `sppCounterDefinitions:1396`, флаги `skipNextGame`/`niglingInjury` и правит казну числом в поле ввода.
- `skipNextGame` при этом исключает игрока и из состава, и из **стоимости команды** (`calculateRosterCosts:7050-7055`) — то есть травма уменьшает TV, что почти наверняка неверно и точно не задокументировано.

Это не «недоделанная фича», а отсутствующее звено доменной модели: у ростера нет понятия «состояние на момент матча».

## 9. Проблема G — сервер и инфраструктура (P1/P2)

- `handleApi` — цепочка из ~60 `if` с регулярками на 680 строк (`server/server.mjs:1301-1980`); маршруты, авторизация, валидация и SQL в одном месте.
- Авторизация сделана добротно: scrypt + соль (`hashPassword:284`), в сессиях хранится sha256 токена (`hashToken:280`), проверка срока в SQL. Нет только rate limiting на `/api/auth/login` и логирования попыток.
- Нет системы миграций — см. 7.7.
- Нет тестов, линтера, typecheck. CI (`.github/workflows/deploy.yml`) делает `git reset --hard` + `npm install` + `npm run build` + `pm2 restart`, без health-check и без отката: сломанный `main` мгновенно уезжает в прод.
- В git закоммичен `dist/` (включая `local-preview.html` на 4,7 МБ), а `scripts/build-site.mjs:72` завязан на точную строку `src/app.js?v=gata-97` из `index.html` — при изменении версии генерация локального превью тихо ломается. Сами версии уже разъехались: `index.html` просит `?v=gata-97` и `styles.css?v=gata-61`, а `assetVersion` в коде — `gata-93` (`src/app.js:108`).
- ~7,1 МБ ассетов не используются: вся папка `assets/section-backgrounds/` (8 JPG, 3,8 МБ) не упоминается ни в CSS, ни в JS, плюс `drishevik.png` (1,6 МБ), `trophy.png` (0,9 МБ), `zbbL-ball.png` (0,8 МБ). Всё это ещё раз лежит в закоммиченном `dist/`.

## 10. Целевая архитектура

Ограничения приняты заказчиком: **vanilla JS + нативные ES-модули, без сборщика и без фреймворка**. Значит, архитектура должна давать безопасность за счёт границ модулей и чистых функций, а не за счёт типов и реактивности.

Правило: **в базе лежит ровно RosterV2**. Миграция старых записей выполняется один раз скриптом, а не при каждом чтении.

### 10.3. Слой сохранения (`data/roster-store.mjs`)

Единственный владелец сохранённых ростеров. Ни один экран больше не вызывает `apiRequest` для команд напрямую.

- **Один объект-истина на команду.** `store.get(id)` возвращает стабильную ссылку; ответ сервера применяется точечным слиянием, объект-черновик никогда не подменяется целиком. Это закрывает гонку 7.2 по конструкции, а не заплаткой.
- **Очередь на команду.** Максимум один активный `PATCH` на `teamId`; правки во время полёта копятся и уходят одним следующим запросом. Порядок записи гарантирован.
- **Оптимистичная блокировка.** Клиент шлёт `revision`, сервер сверяет и на расхождении отвечает `409` с актуальной версией. UI показывает диалог «на сервере более новая версия» с выбором, а не молча затирает.
- **Отказоустойчивость.** Неотправленные изменения кладутся в `localStorage` под ключом `gata-league-pending-roster:<id>`; при возврате на страницу предлагается восстановить. `beforeunload` предупреждает о несохранённом. 401 переводит в явное состояние «сессия истекла, войдите» с сохранением правок.
- **Явные статусы** вместо строки-статуса: `idle | dirty | saving | saved | offline | conflict | error`, отражаются одним компонентом.
- **Черновик билдера** живёт в том же слое и тоже автосохраняется в `localStorage` — путь №2 из таблицы 7.1 перестаёт терять работу.

### 10.4. Ростер в процессе игры

Новая сущность — **снапшот ростера**:

```sql
CREATE TABLE roster_snapshots (
  id UUID PRIMARY KEY,
  saved_team_id UUID NOT NULL REFERENCES saved_teams(id) ON DELETE CASCADE,
  season_id UUID REFERENCES seasons(id) ON DELETE SET NULL,
  round_id  UUID REFERENCES season_rounds(id) ON DELETE SET NULL,
  pairing_id UUID REFERENCES season_pairings(id) ON DELETE SET NULL,
  kind TEXT NOT NULL,          -- 'round_lock' | 'pre_game' | 'post_game' | 'manual'
  roster JSONB NOT NULL,       -- RosterV2 целиком
  team_value INTEGER NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

Жизненный цикл матча:

1. **Старт раунда** — `startSeasonRound` в той же транзакции пишет `kind='round_lock'` для каждого участника. С этого момента экран матча и публичный профиль показывают зафиксированный состав.
2. **Во время раунда** ростер остаётся редактируемым (правила лиги это допускают), но матч ссылается на снапшот. При желании можно включить жёсткий лок — решение за владельцем лиги (см. 13).
3. **После матча** — мастер результата в 3 шага вместо одной формы: счёт → SPP по игрокам (TD/CAS/COMP/INT/MVP, предзаполнено из счёта) → травмы и деньги. По подтверждении сервер атомарно: сохраняет результат, применяет дельту к живому ростеру, пишет `kind='post_game'` снапшот со ссылкой на `pairing_id`.
4. **История** — на профиле команды появляется таймлайн: TV по турам, кто набрал SPP, кто умер. Это и есть то, чего сейчас нет совсем.

Дополнительно: `season_entries.saved_team_id` переводится на `ON DELETE RESTRICT`, а удаление команды, участвующей в активном сезоне, запрещается с внятным сообщением (закрывает 7.6).

### 10.5. Правила лиги в одном месте

`src/domain/league-rules.mjs` — единственный источник чисел: стартовый бюджет, минимум/максимум игроков, цены персонала, цены скиллов и статов, ранги прокачки, элит-комбо. Сборка (`scripts/build-data.mjs`) получает проверку: если число в правилах не совпадает с тем, что написано в `content/Gata/`, сборка ругается. Это убирает молчаливое расхождение «код против текста правил».

## 11. Принятые решения

| # | Решение | Почему так, а не иначе |
|---|---|---|
| D1 | Vanilla JS + ES-модули, без сборщика | Выбор заказчика. Деплой (`pm2` + статика через `server/server.mjs` + Caddy) и Netlify продолжают работать без изменений; рефакторинг катится частями, каждая задача деплоится отдельно. |
| D2 | Один редактор ростера в двух режимах (`create` / `league`) вместо двух реализаций | 12 пар функций-дублей (5.1) — главный источник расхождений поведения. Режим отличается только правилами (бюджет vs казна) и составом панелей. |
| D3 | ~~RosterV2 + одноразовая миграция~~ → **поддержка старых форматов просто удалена** (решение владельца 2026-08-19) | Изначально предполагалось привести все блобы к RosterV2 скриптом. Владелец подтвердил, что старых форматов в базе не осталось, поэтому вместо переписывания данных убран сам код чтения — минус два поколения формата, минус 43 функции, минус единственная необратимая операция плана. Страховка — `scripts/check-roster-shapes.mjs` перед выкатом. См. 6.1. |

## 14. Проблема H — сервер отдаёт наружу файлы репозитория (P0, эксплуатируется без аутентификации)

`resolveStaticPath` (`server/server.mjs:1982-1987`):

```js
const target = cleanPath === "/" ? "index.html" : cleanPath.slice(1);
const fullPath = path.resolve(rootDir, target);
return fullPath.startsWith(rootDir) ? fullPath : null;
```

`rootDir` — корень репозитория (`/opt/bloodbowl-league` на бою). Проверка запрещает выход **выше** корня, но не ограничивает выдачу каталогами статики. Всё, что лежит в папке деплоя, доступно по HTTP любому:

| Запрос | Что отдаётся |
|---|---|
| `GET /.env` | `POSTGRES_PASSWORD`, `DATABASE_URL` с паролем, `ADMIN_LOGIN`, `ADMIN_PASSWORD` |
| `GET /.git/config`, `/.git/…` | вся история репозитория (деплой делает `git reset --hard`, каталог `.git` на месте) |
| `GET /server/server.mjs`, `/server/init.sql` | исходники и схема БД |
| `GET /docker-compose.yml`, `/package.json` | инфраструктурные файлы |

Расширение файла роли не играет: неизвестный тип отдаётся как `application/octet-stream` (`handleStatic:2004-2022`), файлы без расширения — тоже. Единственная развилка перед статикой — `url.pathname.startsWith("/api/")` (`server/server.mjs:2031`), белого списка нет.

**Проверено на бою:** `https://bloodbowlyerevan.shitpostsoftware.com/package.json` отдаёт содержимое файла из репозитория. `.env` намеренно не запрашивался, но подпадает под то же правило.

**Цепочка усиления, из-за которой это критично, а не просто неприятно:**

1. `docker-compose.yml:14-15` публикует Postgres как `"${POSTGRES_PORT:-5433}:5432"` — это привязка к `0.0.0.0`, порт виден снаружи. `DEPLOYMENT.md:160-169` описывает правила `ufw` только для порта 3002. Утёкший пароль + открытый порт = прямой доступ к базе.
2. `ensureAdmin` (`server/server.mjs:343-362`) при каждом старте процесса перезаписывает пароль администратора значением из `.env` (`ON CONFLICT … DO UPDATE SET password_hash = EXCLUDED.password_hash`). То есть утёкший `.env` даёт админский вход и после смены пароля через интерфейс — пока не изменён сам файл.
3. Токены сессий лежат в `localStorage` (`src/app.js:981`), а ответы сервера не имеют ни одного security-заголовка: ни `Content-Security-Policy`, ни `X-Content-Type-Options`, ни `Referrer-Policy`. Конфиг Caddy (`deploy/caddy/bloodbowlyerevan.shitpostsoftware.com.conf`) — голый `reverse_proxy` без заголовков.

**Порядок устранения** — задача S плана: ограничить статику белым списком каталогов, сменить пароли БД и админа, увести публикацию Postgres на `127.0.0.1`, проверить логи на обращения к `/.env` и `/.git`.

## 15. Проблема I — целостность результатов матчей (P1)

**15.1. Игрок может подтвердить собственный результат.** `respondToGameProposal` (`server/server.mjs:1127-1143`) проверяет, что пользователь участвует в матче и что статус `awaiting_confirmation`, но **не сравнивает** `userId` с `proposed_by_user_id`. Клиент показывает блок подтверждения по условию `awaitingConfirmation && !resultSubmitted && !playerLocked` (`src/app.js:4091-4094`) — тоже без учёта авторства. Значит, игрок подаёт счёт и тут же жмёт «Подтвердить» за соперника; двухсторонняя схема подтверждения обходится в два клика.

Показательно, что поле `viewerIsProposer` **вычисляется** сервером и уходит клиенту (`publicGame:682`), но не используется ни там, ни там: `grep viewerIsProposer src/app.js` — ноль совпадений. Проверку задумали и не довели.

**15.2. Подтверждение результата — три отдельных запроса без транзакции.** `respondToGameProposal` вызывает `updateSeasonPairing` (внутри — свой `UPDATE`), затем отдельным запросом ставит `result_status='confirmed'`. Сбой между ними оставляет матч с посчитанными очками, но в статусе ожидания (или наоборот). При этом `startSeasonRound` (`1248`) транзакцию использует — то есть в одном файле два разных подхода.

**15.3. Правила начисления очков зашиты в сервер.** `scoreLeagueResult` (`server/server.mjs:708-737`): 3 за победу, 1 за ничью, +1 за разрыв ≥3 тачдаунов, +1 за «сухую» победу, +1 за ≥4 кэжуалти. Те же числа отдельно описаны в тексте правил лиги. Это ровно та же болезнь, что и бюджет 600 в билдере (раздел 5.3), только на сервере — и лечится тем же `league-rules`.

**15.4. Таблица считает не всё, что собирает.** `computeSeasonStandings` (`740-808`) наполняет массив `opponents` для каждого участника и отдаёт его клиенту, но сортировка идёт по очкам → тачдаунам → кэжуалти → числу игр → логину (`801-806`). Тайбрейка по силе соперников (Бухгольц), ради которого `opponents` и собирался, нет. Для швейцарской системы это основной тайбрейк.

**15.5. Швейцарка — жадный алгоритм без возврата.** `generateSwissRound` (`959-1047`) идёт по очереди сверху и для каждого берёт **первого** соперника, с которым ещё не играли; если такого нет — первого попавшегося (`awayIndex = 0`). Корректная пара может существовать, но алгоритм её не найдёт и создаст повтор. Для лиги на 8–16 команд это редкий, но реальный случай; лечится либо перебором с возвратом, либо явным предупреждением админу «пара-повтор, проверьте вручную».

## 16. Проблема J — i18n за пределами билдера (P1)

В первой части сказано, что предупреждения ростера (`rosterWarnings:7078-7086`) — «единственная дыра». Второй проход показал, что дыр больше: **около 30 строк интерфейса и все сообщения сервера идут мимо `t()`**.

**16.1. Нужен либо явный реестр динамических ключей, либо замена шаблонных ключей на таблицы соответствия.

**16.2. `npm run i18n:check` проверяет не то, что обещает.** `scripts/check-i18n-glossary.mjs` (58 строк) сверяет только идентификаторы, заголовки и пути страниц между `data.en.json` и `data.ru.json`. Он не проверяет ни глоссарий терминов (несмотря на название), ни словари интерфейса `src/i18n/*.json`, ни фактическую переведённость страницы: страница, для которой RU-файла нет и который подменяется английским оригиналом (`resolveLocaleFiles:651-663`), проходит проверку как успешная.

## 19. Проблема M — производительность и гигиена сервера (P2)

**19.1. Синхронное сжатие на каждый ответ, без кеша.** `encodedBody` (`server/server.mjs:376-392`) вызывает `brotliCompressSync` (качество 5) или `gzipSync` (уровень 6) для каждого подходящего ответа. `public/data.<locale>.json` — 1,67 МБ; он пережимается заново **для каждого посетителя**, блокируя единственный поток Node на всё время сжатия. Пока идёт сжатие, сервер не обслуживает никого. Лечение: пережать статику один раз на сборке (`.br`/`.gz` рядом с файлом) и отдавать готовое, либо кешировать сжатый буфер в памяти по mtime.

**19.2. Сессии не чистятся.** Записи удаляются только при явном выходе (`1356`) и при удалении пользователя (`1461`). Истёкшие сессии остаются в таблице навсегда, хотя индекс `sessions_expires_at_idx` для их удаления уже есть.

**19.3. Нет ограничения частоты входа.** `POST /api/auth/login` (`1340`) не ограничен ничем; пароли проверяются `scryptSync` — то есть каждая попытка ещё и блокирует поток на десятки миллисекунд. Это одновременно и подбор пароля, и способ положить сервер.

**19.4. Нет security-заголовков** ни в ответах Node, ни в Caddy: отсутствуют `Content-Security-Policy`, `X-Content-Type-Options: nosniff`, `Referrer-Policy`, `Permissions-Policy`. При хранении токена в `localStorage` CSP — основной барьер против кражи токена при XSS.

**19.5. Деплой без проверки и без отката.** `.github/workflows/deploy.yml`: `git reset --hard` → `npm install` → `npm run build` → `pm2 restart`. Нет проверки `/api/health` после рестарта, нет отката на предыдущий коммит, нет шага миграций БД (схема применяется на старте процесса — см. 7.7). Сломанный `main` уезжает в прод мгновенно и молча.
